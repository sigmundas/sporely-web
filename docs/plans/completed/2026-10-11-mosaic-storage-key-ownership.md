# Enforce spore-mosaic storage-key ownership (security fix)

Status: **completed 2026-10-11.** Stage 1 was accepted (security review APPROVE
on `4e58763`) and merged to `main` at `0af1e32`. Stage 2 was executed in
production by the owner; see "Closing entry" at the end. Approved 2026-10-11 by
the owner, with the decisions recorded below. Was `docs/plans/active/` until
closed 2026-10-11.
Repository: `sporely-web`. Branch: `fix/mosaic-storage-key-ownership` from
`main` (`5739b9a`). Independent of `feature/batch-spore-preview-rpc`, which is
paused at its Stage 1 gate until this plan completes.
Priority: high. The flaw is pre-existing in production.

## Why

Any signed-in user who owns a public observation can serve another user's R2
object through the Worker.

**How it works today:**
- The mosaic INSERT/UPDATE RLS checks only `user_id = auth.uid()` and that the
  caller owns the observation
  (`supabase/migrations/20260702100000_add_spore_measurement_mosaics.sql:69-96`).
- The only mosaic row trigger is the BEFORE UPDATE version bump
  (`20260804120000_media_authorization.sql:628-646`).
- Nothing validates `id`, `storage_key`, `canonical_bucket` or `media_version`
  on INSERT. `id` is `GENERATED BY DEFAULT` (`20260702100000:18`). On UPDATE,
  `storage_key` and `canonical_bucket` can change freely.
- `media_authorize_mosaic_delivery` (`20260804120000:850-976`) checks only that
  the mosaic's `user_id` equals the observation owner (`owner_mismatch`,
  `:903-906`). It then returns `r.storage_key` to the owner (`:913-918`) and to
  eligible viewers (`:960`). It never checks that the key lies in the owner's
  namespace.
- The Worker's `/mm/` handler fetches `decision.storage_key` from
  `decision.canonical_bucket` without any key check
  (`cloudflare/r2-upload-worker/src/index.js:1938-1997`).
- The same RPC gates `get_observation_spore_mosaic`
  (`20260825092647_get_observation_spore_mosaic_rpc.sql:32`).

**Further effects:**
- **Availability:** a client can claim ids ahead of the sequence, so other
  users' default-id inserts collide.
- **Account deletion:** `delete-account` snapshots every mosaic key
  (`supabase/functions/delete-account/plan.js:131-150`), and the Worker DELETE
  refuses keys outside the caller's prefix (`index.js:871-877`). A malformed row
  therefore breaks deletion of the attacker's own account. The victim's object
  is not deleted.

**The reference design is the image path, which does not have this flaw:**
- BEFORE guards for server-owned fields and key ownership, plus an AFTER
  final-state guard (`20260804120000:251-310, 361-408, 454-529`).
- Read-time namespace checks (`:762-795`).
- `observation_images.id` is `GENERATED ALWAYS`
  (`20260521120000_baseline_live_public_schema.sql:1015`).

## Fixed decisions

- **Ownership convention (owner decision): a storage key must start with
  `<user_id>/`**, where `user_id` is the row owner's uuid text and the owner
  equals the observation owner. Evidence:
  - Worker uploads require `key.startsWith(claims.sub + '/')`
    (`index.js:384-388`).
  - Private-mode uploads keep the same key; only the bucket changes
    (`index.js:1646-1661`).
  - Replacement keys sit under `<sub>/<observation_id>/` (`index.js:1876-1886`).
  - sporely-py builds `{user}/{obs}/spore_mosaic_v{n}_{digest}.webp`.
  - The image path uses the same `<user_id>/` rule (`20260804120000:496-511, 786-795`).
  - The stricter `<user_id>/<observation_id>/` rule is NOT enforced.
- **No exceptions for shared, admin or backfilled keys.**
  - Service-role writes (`auth.uid() IS NULL`) skip the write guard, as images
    do. The Worker's `markMosaicCanonicalBucketPrivate` PATCH needs this
    (`index.js:1924-1936`).
  - The read-time check applies to every row, including rows written by a
    trusted role.
- **Write time (new migration):**
  - `id` becomes `GENERATED ALWAYS`. sporely-py never sends `id`. Advance the
    identity sequence to `GREATEST(max(id), last_value)` so ids that were
    already claimed cannot collide.
  - Three guards mirror the image path:
    - `trg_00_media_guard_server_owned_mosaic` (BEFORE INSERT/UPDATE):
      - INSERT requires `canonical_bucket = 'legacy'` and `media_version = 1`.
      - UPDATE: client roles may not change `canonical_bucket`, and
        `media_version` may change only as a nested +1.
    - `trg_01_media_guard_key_ownership_mosaic` (BEFORE INSERT/UPDATE,
      SECURITY DEFINER, trusted when `auth.uid() IS NULL`):
      - `NEW.user_id` must equal `auth.uid()` and the observation owner.
      - On INSERT, or when `storage_key` changes, the key must start with
        `<user_id>/`.
      - The key must contain no `.`/`..` segments, empty segments, leading `/`,
        backslash or control characters (parity with `normalizeObjectKey`,
        `index.js:1585-1601`).
    - `trg_zz_media_final_state_guard_mosaic` (AFTER INSERT/UPDATE):
      - Client INSERT must end with version 1 and bucket `legacy`.
      - Client UPDATE may change the version by 0 or +1 only, and may not
        change the bucket.
  - The key check runs only when the key changes. Otherwise an existing
    malformed row would make the owner's observation updates fail through the
    version cascade (`20260804120000:648-669`).
  - Trigger names sort so the guards run before `trg_mosaic_media_version_bump`.
  - Revoke EXECUTE on all new functions from PUBLIC, anon and authenticated.
- **Read time:** `CREATE OR REPLACE public.media_authorize_mosaic_delivery`,
  with the signature and RETURNS TABLE unchanged.
  - Add the deny reason `invalid_storage_namespace`. It applies when the key does
    not start with `mosaic_user_id::text || '/'`, or has a dot or empty segment.
  - Place the check after `no_key` and **before the owner branch** (`:913`),
    because the attacker owns the malformed row.
  - Re-issue the REVOKE from PUBLIC/anon/authenticated, the GRANT to
    service_role, and the COMMENT.
  - `get_observation_spore_mosaic` inherits the new check.
- **Worker (owner decision): database-only.**
  - No Worker production change and no deploy.
  - One Worker regression test pins that `/mm/` returns 404 and never reads the
    bucket when the RPC returns `invalid_storage_namespace`.
- **Existing malformed rows (owner decision: apply and neutralize).**
  - The migration itself changes no data. The read-time check denies malformed
    rows as soon as it is applied.
  - If the production probe finds any, a person first takes a private forensic
    snapshot outside any agent context. A person then runs an owner-approved
    neutralization step (Stage 2).
  - A non-zero probe may indicate exploitation involving personal data. The
    owner decides on a breach assessment. Agents never see the offending rows.
- **Migration version (owner decision): `20261011100000_enforce_mosaic_storage_key_ownership.sql`.**
  - It is later than main's latest (`20261007123912`) and earlier than the
    paused, unapplied batch migration `20261011120000`, which keeps its name.
  - Applied versions are never renamed or repaired.
- **Out of scope:**
  - `get_public_observation` / `_get_public_observation_stage2a`. The raw `url`
    is handled later by the batch "fail closed" change and a separate reviewed
    change.
  - The image path.
  - Sequence privileges.
  - Worker source.
  - Regenerating `supabase/schema.sql`.
- **No production connection** for implementation or review (see
  `.sparring/PROJECT.md`). Agents perform no production reads or writes,
  deploys or exploit tests. Work against migrations and a local
  `supabase db reset` only.

### Pre-flight probe (read-only, aggregate-only, run by a person)

    BEGIN TRANSACTION READ ONLY;
    SELECT
      count(*)                                                        AS total,
      count(*) FILTER (WHERE coalesce(m.storage_key,'') = '')         AS empty_key,
      count(*) FILTER (WHERE starts_with(m.storage_key, m.user_id::text||'/')) AS owner_prefixed,
      count(*) FILTER (WHERE NOT starts_with(coalesce(m.storage_key,''), m.user_id::text||'/')) AS not_owner_prefixed,
      count(*) FILTER (WHERE NOT starts_with(coalesce(m.storage_key,''), m.user_id::text||'/')
                       AND m.storage_key ~ '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/') AS foreign_uuid_prefixed,
      count(*) FILTER (WHERE m.storage_key ~* '^(https?://|/)')       AS url_or_leading_slash,
      count(*) FILTER (WHERE m.storage_key ~ '(^|/)\.{1,2}(/|$)' OR m.storage_key ~ '//' OR strpos(m.storage_key, chr(92)) > 0) AS bad_segments,
      count(*) FILTER (WHERE m.user_id IS DISTINCT FROM o.user_id)   AS owner_mismatch,
      count(*) FILTER (WHERE m.id <= 0)                               AS nonpositive_id,
      count(*) FILTER (WHERE m.canonical_bucket = 'private')         AS private_bucket,
      count(*) FILTER (WHERE m.media_version > 1)                    AS version_gt_1,
      count(DISTINCT m.user_id) FILTER (WHERE NOT starts_with(coalesce(m.storage_key,''), m.user_id::text||'/')) AS owners_with_bad_keys,
      (SELECT count(*) FROM (SELECT storage_key FROM public.spore_measurement_mosaics
                             GROUP BY storage_key HAVING count(DISTINCT user_id) > 1) d) AS keys_shared_across_users,
      (SELECT max(id) FROM public.spore_measurement_mosaics)         AS max_id,
      (SELECT last_value FROM public.spore_measurement_mosaics_id_seq) AS seq_last_value
    FROM public.spore_measurement_mosaics m
    JOIN public.observations o ON o.id = m.observation_id;
    ROLLBACK;

Output is counts and integers only: no keys, user ids or observation ids. How
to read it:
- **Possible exploitation → incident handling, then neutralization (Stage 2):**
  `not_owner_prefixed`, `bad_segments` or `nonpositive_id` above 0, or
  `max_id > seq_last_value`.
- **Legitimate rows in a non-canonical form would be denied:**
  `url_or_leading_slash > 0`. The owner decides on normalization before Stage 1
  is accepted.
- **Suspicious while production runs `MEDIA_STORAGE_MODE=legacy`:**
  `private_bucket > 0`.

## Stage 1 — Write/read guards, regression tests, security review

First read the sections above the stages in `docs/plans/active/2026-10-11-mosaic-storage-key-ownership.md`. Their decisions and constraints apply to this stage.

Scope (all in `sporely-web`):
1. **Migration.** Add
   `supabase/migrations/20261011100000_enforce_mosaic_storage_key_ownership.sql`,
   wrapped in BEGIN/COMMIT. It contains:
   - `ALTER TABLE public.spore_measurement_mosaics ALTER COLUMN id SET GENERATED ALWAYS;`
   - the sequence `setval`;
   - the three guard functions and triggers;
   - the replaced `media_authorize_mosaic_delivery`.

   Do not edit any existing migration.
2. **pgTAP suite.** Add `supabase/tests/mosaic_storage_key_ownership_test.sql`,
   run with `supabase test db <file>`. Cases:
   - **Setup.** Authenticated as attacker A, who owns a public observation with
     public spore data.
   - **INSERT is rejected** (`42501`, or `428C9` for an explicit id) when it has:
     - a key under another user V's prefix;
     - an explicit id, both negative and ahead of the sequence;
     - `canonical_bucket='private'`;
     - `media_version=7`;
     - the full incident combination (`id=-5`, foreign key, `private`, 7);
     - a `<A>/../<V>/x` key.
   - **UPDATE of A's own row is rejected** when it moves the key to V's prefix,
     changes the bucket, sets an arbitrary `media_version`, or changes `id`.
   - **Legitimate paths succeed:**
     - a sporely-py-shaped insert, `<A>/<obs>/spore_mosaic_v1_<hex>.webp`
       → id > 0, version 1, bucket `legacy`;
     - a replacement key under `<A>/<obs>/` → version +1 exactly;
     - an identical update that includes `updated_at` → no version change;
     - a service-role (no `sub`) `canonical_bucket='private'` update, which is
       the Worker path;
     - an owner visibility change → mosaic version +1 through the cascade,
       **including on an observation that holds a trusted-inserted malformed
       row**.
   - **Read time.** A postgres-inserted row where `user_id` = observation owner
     = A, with the key under `<V>/`:
     - is denied with `invalid_storage_namespace` and `storage_key IS NULL` for
       A as owner, anon, a stranger and A's friend;
     - `get_observation_spore_mosaic` returns no row for it.
   - **Grants.** `media_authorize_mosaic_delivery` remains executable by
     service_role only, and the new guard functions are not executable by
     anon or authenticated.
3. **Worker test.** In `cloudflare/r2-upload-worker/src/index.test.js`,
   `/mm/<id>?v=<n>` returns 404 and never calls `bucket.get` when the RPC
   returns `allowed:false, reason:'invalid_storage_namespace'`. The existing
   Stage2h mosaic upload tests (`:1280-1420`) must stay green unchanged.
4. **Re-run every suite that inserts mosaics or calls the mosaic RPC.** Adjust
   fixtures only where they insert explicit ids as authenticated:
   - `media_authorization_test.sql` (Section K `:1012+`);
   - `observation_spore_mosaic_rpc_test.sql`;
   - `stage2b_authorized_media_projections_test.sql`;
   - `public_observation_rpc_validation.sql` (`:2186`);
   - `metadata_only_microscope_images_test.sql` (`:116`);
   - `observation_microscopy_presentations_test.sql` (`:184`).
5. **Docs.** Add a short note to the mosaic section of
   `docs/security/stage-2-media-authorization.md` covering the guards and the
   `invalid_storage_namespace` reason.

## Stage 2 — Production migration runbook (human-executed)

First read the sections above the stages in `docs/plans/active/2026-10-11-mosaic-storage-key-ownership.md`. Their decisions and constraints apply to this stage.

The agent writes
`docs/deployments/2026-10-11-mosaic-storage-key-ownership-runbook.md`. It
executes nothing and connects to nothing. The runbook covers:

1. **Pre-checks.** `supabase migration list` shows local = remote, except the
   documented deferred `20260914090000` (`supabase/deploy-exceptions.json`).
   Remote's latest is ≤ `20261007123912`. Otherwise STOP and report.
2. **Probe.** Run the pre-flight probe above and record its aggregate output.
3. **Incident branch, only if the probe shows possible exploitation:**
   1. A person takes a private forensic snapshot of the offending rows (id,
      observation id, owner, key, bucket, version, timestamps), stored under the
      data controller's incident procedure and never pasted into agent context.
   2. The owner decides whether to make a personal-data breach assessment.
   3. After the migration is applied, an owner-approved **neutralization step**
      runs as a single reviewed transaction. The runbook provides the SQL, which
      deletes the namespace-invalid mosaic rows (tiles cascade) and reports only
      affected-row counts, which must match the probe. Deleting rather than
      rewriting is preferred: a rewritten key would point at no object, and the
      row still advertises a foreign raw URL through `get_public_observation`
      until it is removed. If the owner prefers to keep the rows, the runbook
      gives the alternative of reassigning them to an inert state, with its
      trade-offs.
4. **Apply.**
   1. `node scripts/supabase-deploy-tree.mjs prepare --allow 20261011100000 --ref <merged main SHA>`
   2. `check`
   3. `supabase db push --linked` inside the tree
   4. `post-verify`
   5. Remove the tree.
5. **Verify (read-only):**
   - `pg_attribute.attidentity = 'a'` for the mosaic `id`;
   - the three triggers are present in `pg_trigger`;
   - the `prosrc` of `media_authorize_mosaic_delivery` contains
     `invalid_storage_namespace`;
   - `has_function_privilege('authenticated', …, 'EXECUTE')` is false for the
     authorize and guard functions;
   - this aggregate returns 0:
     `SELECT count(*) FILTER (WHERE a.allowed) FROM public.spore_measurement_mosaics m CROSS JOIN LATERAL public.media_authorize_mosaic_delivery(m.id, m.user_id) a WHERE NOT starts_with(coalesce(m.storage_key,''), m.user_id::text||'/')`;
   - a person syncs one new mosaic and one replacement mosaic with a test
     account from the current sporely-py, and views them in the app and on the
     landing site.
6. **Rollback / compensation.**
   - Fix forward by default.
   - If legitimate sync breaks, ship a NEW compensating migration that drops the
     three triggers and functions, restores the `20260804120000:850-976`
     function body, and sets `id` back to BY DEFAULT. This re-opens the flaw,
     so it needs owner approval.
   - Never use `migration repair`, and never edit applied files.

Human gate: only a person, with explicit authorization, performs steps 1–6 and
records the evidence. Nothing is deployed automatically.
